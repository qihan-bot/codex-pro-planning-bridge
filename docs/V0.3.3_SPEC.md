# Codex Pro Planning Bridge v0.3.3 Specification

Status: Implemented in `v0.3.3-beta`.

## Snapshot Schema

The Workflow Runtime stores complete, local, JSON-only runtime snapshots under:

```text
.codex/workflow/snapshots/
├── 001.json
├── 002.json
└── latest.json
```

Each numbered snapshot is immutable after creation. `latest.json` is a
deterministic copy of the newest numbered snapshot and is safe to replace when
a newer snapshot is created.

Every snapshot must contain:

```json
{
  "schema_version": 1,
  "snapshot_id": 2,
  "timestamp": "2026-08-20T12:00:00Z",
  "workflow": {
    "state": "VALIDATING",
    "history_position": 7
  },
  "plan": {
    "path": ".codex/pro-plan/PLAN.md",
    "sha256": "<64 hexadecimal characters>"
  },
  "approval": {
    "status": "APPROVED",
    "plan_sha256": "<64 hexadecimal characters>",
    "approved_by": "user",
    "timestamp": "2026-08-20T11:59:00Z"
  },
  "repository": {
    "commit": "<40 hexadecimal characters or null>",
    "dirty": false
  },
  "memory": {
    "version": 1
  }
}
```

The field order and JSON formatting are stable. Paths are repository-relative
POSIX paths whenever the referenced file is inside the repository. Snapshot
creation never edits source files, `PLAN.md`, approval artifacts, event
records, or project-memory documents.

## Recovery Model

Recovery restores a complete runtime context from a validated snapshot instead
of inferring state from a single event. The recovery engine must:

1. select an explicit snapshot or the newest valid `latest.json`;
2. verify the snapshot schema and all referenced paths and hashes;
3. verify that the event ledger contains at least the recorded
   `history_position`;
4. restore workflow metadata from the snapshot; and
5. append a compensating recovery event without deleting prior events.

Recovery is metadata-only. It must never modify repository source files, plan
contents, approval contents, Git commits, or project-memory documents. If no
valid snapshot exists, or if the event ledger and snapshot disagree, recovery
must fail closed with an actionable diagnostic rather than guessing a state.

## Integrity Rules

`cpb resume` must run an integrity check before resuming a workflow. The check
must compare:

- `state.json` against the selected snapshot;
- the snapshot history position against `events.jsonl` and `history.json`;
- the current `PLAN.md` path and SHA-256 hash against the snapshot;
- the current approval status and plan hash against the snapshot;
- the recorded repository commit and dirty state against local Git; and
- the recorded Project Memory schema version against `memory.json`.

The command prints:

```text
Workflow Integrity: PASS
```

or:

```text
Workflow Integrity: FAILED
- <actionable reason>
```

Integrity checking is read-only. A failed check blocks `resume` and identifies
the first mismatch without rewriting any runtime artifact.

## Approval Lifecycle

Approval records expose an explicit lifecycle status:

```text
APPROVED
INVALIDATED
EXPIRED
REVOKED
```

The lifecycle rules are:

- a matching human approval starts as `APPROVED`;
- changing, replacing, or deleting `PLAN.md` changes the effective status to
  `INVALIDATED`;
- an approval past its configured validity window becomes `EXPIRED`;
- an explicit user revocation becomes `REVOKED`; and
- only `APPROVED` with matching plan path and SHA-256 hash may authorize the
  `IMPLEMENTING` transition.

Lifecycle changes are represented in the approval artifact and recorded in the
append-only workflow event ledger. Re-approval creates a new approval time and
hash; it does not silently reactivate an invalidated, expired, or revoked
record.
